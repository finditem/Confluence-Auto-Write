# 프론트+백엔드 통합 주간 회의록 (계획, 미착수)

> 상태: 설계 중 — 아직 코드 작업 시작 안 함. 아래 미정 사항 정리되면 착수.

## 왜 필요한가

지금은 프론트엔드 팀 전용 주간 회의록만 자동 생성됨 (`frontend/weekly_report.py`, 이 저장소).

백엔드 팀이 프론트 관련 공유사항을 확인하려고 프론트엔드 회의록 전체를 읽는 건 리소스 낭비라고 판단. 대신 양 팀이 같이 보는 **통합 회의록**을 따로 만들고, 거기서 필요한 내용만 모아서 보는 방향으로 감.

이 논의 과정에서 프론트엔드 회의록에 "4. 백엔드 미팅 공유 사안" 섹션을 추가함(이미 반영됨) — 프론트팀이 백엔드가 알아야 할 내용을 여기 적어두면, 그 내용이 통합 회의록으로 옮겨지는 소스가 됨.

## 확정된 흐름

1. 통합 회의 요일/시간에 맞춰 **별도 GitHub Actions 크론**이 실행됨 (프론트 전용 크론과 별개)
2. 그 시점 기준 **그 주 월요일에 생성된 프론트엔드 회의록 페이지**를 찾음 (이번 주 프론트 회의록 = 소스)
3. 그 페이지에서 **"4. 백엔드 미팅 공유 사안" 섹션 내용만 파싱해서 추출**
4. (예정) 같은 방식으로 **백엔드 회의록의 "프론트 미팅 공유 사항" 섹션**도 파싱해서 추출 — [backend-report-plan.md](./backend-report-plan.md)에서 그쪽 자동화가 먼저 준비돼야 함
5. 통합 회의록 페이지(신규 생성/갱신)에 양쪽 내용을 기입 → **양방향 구조로 방향 잡힘** (프론트→백엔드, 백엔드→프론트 둘 다)

**섹션 이름 매핑** (소스 문서 기준 이름 → 통합 회의록 기준 이름, 관점이 뒤집힘에 주의):

| 소스 | 소스 문서의 섹션명 | 통합 회의록의 섹션명 |
|---|---|---|
| 프론트 회의록 | "백엔드 미팅 공유 사안" (백엔드가 알아야 할 것) | **"프론트 공유 사안"** (프론트가 공유하는 것) |
| 백엔드 회의록 | "프론트 미팅 공유 사항" (프론트가 알아야 할 것) | **"백엔드 공유 사안"** (백엔드가 공유하는 것) |

## 통합 회의록 템플릿 구조 (확정)

프론트 회의록과 동일한 스타일(번호 1./2./3./4. + 참가자/작업 항목은 a./b./c. 들여쓰기)로 감.

```
🗓️ 날짜
   [실행일]

👥 참가자 (팀별로 나눠서 표기)
   프론트엔드: 서지권, 이수현, 김준열
   백엔드: 유세정

1. 프론트 공유 사안
   (프론트 회의록의 "백엔드 미팅 공유 사안" 섹션에서 자동으로 가져와 채워짐)

2. 백엔드 공유 사안
   (백엔드 회의록의 "프론트 미팅 공유 사항" 섹션에서 자동으로 가져와 채워짐)

3. 전체 회의 공유 사안
   (통합 회의 중 결정된 내용을 여기서 직접 작성 — 각 팀 회의록에는 더 이상 안 둠, 통합 회의록에서만 관리)

4. 공유/이슈/질문 공유
   (개발팀 내부 사항, 필요시 작성 — 프론트 회의록과 동일한 이름으로 통일)
```

**중요 — 각 팀 회의록도 같이 바뀌어야 함:**
- 프론트 회의록의 "5. 전체 회의 공유 사안" 섹션은 **통합 회의록으로 이관되면서 제거** 대상 (중복 관리 방지)
- ✅ **완료** — 통합 회의록이 아직 없는 상태지만, 팀장 보고 예정이라 미리 제거함. `frontend/weekly_report.py`에서 "5. 전체 회의 공유 사안" 섹션 삭제 반영 (이제 1~4번만 있음)
- 백엔드 회의록도 처음 설계할 때부터 "전체 회의 공유 사안" 섹션 없이 만들면 됨 (애초에 안 넣으면 되니 이관 이슈 없음)
